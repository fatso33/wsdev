# Flight Deck Widget Studio

The visual design environment and testbench for custom widgets complying with the Flight Deck Widget Standard (FDWS), current version v1.23 (see [`../docs/FlightDeck-Widget-Standard-v1.23.md`](../docs/FlightDeck-Widget-Standard-v1.23.md), a delta spec over [v1.22](../docs/FlightDeck-Widget-Standard-v1.22.md), [v1.21](../docs/FlightDeck-Widget-Standard-v1.21.md), [v1.20](../docs/FlightDeck-Widget-Standard-v1.20.md), [v1.19](../docs/FlightDeck-Widget-Standard-v1.19.md), [v1.18](../docs/FlightDeck-Widget-Standard-v1.18.md), [v1.17](../docs/FlightDeck-Widget-Standard-v1.17.md), [v1.16](../docs/FlightDeck-Widget-Standard-v1.16.md), [v1.15](../docs/FlightDeck-Widget-Standard-v1.15.md), [v1.14](../docs/FlightDeck-Widget-Standard-v1.14.md), [v1.13](../docs/FlightDeck-Widget-Standard-v1.13.md), [v1.12](../docs/FlightDeck-Widget-Standard-v1.12.md), [v1.11](../docs/FlightDeck-Widget-Standard-v1.11.md), [v1.10](../docs/FlightDeck-Widget-Standard-v1.10.md), [v1.9](../docs/FlightDeck-Widget-Standard-v1.9.md), [v1.8](../docs/FlightDeck-Widget-Standard-v1.8.md), [v1.7](../docs/FlightDeck-Widget-Standard-v1.7.md), [v1.6](../docs/FlightDeck-Widget-Standard-v1.6.md), [v1.5](../docs/FlightDeck-Widget-Standard-v1.5.md), [v1.4](../docs/FlightDeck-Widget-Standard-v1.4.md), [v1.3](../docs/FlightDeck-Widget-Standard-v1.3.md), and [v1.2](../docs/FlightDeck-Widget-Standard-v1.2.md)). Plain static HTML/CSS/JS, meant to run in a desktop web browser — no build step. The Component Palette and Specification Validator are fully up to date with the FDWS v1.2 catalog, v1.3 Widget Popovers are supported end-to-end (design, live-preview, and export), `StudioValidator.js` warns on a malformed v1.4 `revision` field, and `core.gauge`'s v1.5 `props.compose` renders correctly in Device View live-preview (`widget-studio/widgets/components/GaugeComponent.js`). See the root [`../README.md`](../README.md) and [`../CHANGELOG.md`](../CHANGELOG.md) for what v1.6 through v1.17 each added — this paragraph hasn't been kept current version-by-version, only re-pointed to the latest. **v1.18 (manual per-theme styling)** is fully supported in the widget-root Inspector's new "THEME" group — see the "Live Theme Preview" bullet below.

- **Edit View & Device View**: Design widgets on a drag-and-resize canvas or preview inside device frames (Compact, Standard Mobile, Tablet, Tablet Pro). Both viewports auto-fit their zoom to the open widget's actual grid size whenever it loads or you switch into that view (was a flat 100%/no-op "Fit" before 2026-08-27 — a widget larger than the viewport, or a tall mobile-portrait device, silently opened clipped). Device View's active widget can always be repositioned precisely via the Col/Row fields; a **Move Widget** toggle (added 2026-08-27, next to those fields) additionally shows a small drag handle on the widget's corner for freehand dragging — off by default, since the handle is a blue overlay that covers a bit of the widget's own content and most of the time you're just looking at/interacting with it, not repositioning it. Interactive Sim mode (a separate live-interactive canvas alongside Design mode) was removed 2026-08-27 — Device View is now the one place to test live interactions, and gets everything Interactive Sim had (real component renderers, real taps/longpresses, reactive `visibleWhen`/compose bindings) plus a realistic device frame Interactive Sim never had.
- **Live Theme Preview**: a sun/moon toggle — one in the canvas toolbar, a matching one in Device View's own header bar (added 2026-08-27, since the canvas toolbar isn't visible while you're in Device View; both there and in the canvas toolbar it sits with the grid-overlay toggle right next to the zoom controls, not scattered elsewhere in the header) — previews what a widget's literal authored colors and gradients will look like under the Flight Deck PWA's light theme — the same derivation `BaseComponent.applyStyles()` applies automatically at runtime (`shared/widgets/components/ThemeColor.js`). Both toggles share one flag (`StudioState.previewTheme`), so flipping either keeps the other in sync. Studio's own UI chrome stays dark regardless of the toggle — only the widget preview surfaces react.
- **"Only Run If" interaction condition (FDWS v1.23, added 2026-08-29)**: the Add/Edit Interaction Trigger modal gained an optional condition — same state/operator/value row style as Conditional Formatting — that must evaluate true for that interaction's action (and feedback) to fire at all. Added after a preset button was found dispatching an invalid `0.000` frequency when tapped while still unset; `visibleWhen` couldn't fix this without also hiding the button's long-press-to-set affordance. A hand-authored compound `allOf`/`anyOf` condition isn't editable through this row — only a single leaf condition, same scope as Conditional Formatting's own rows. `StudioValidator.js` cross-checks the condition's state path the same way it already does for `fromStateRef`.
- **State/operator/value editor rows no longer collapse (fixed 2026-08-29)**: this new condition row initially rendered with its state picker squeezed to ~18px wide. Root cause turned out to be pre-existing, not new — `.prop-select`/`.prop-input`'s own `width:100%` corrupts a bare flex row's `flex-basis:auto` resolution, and the same bug (just never reported) was already present in Conditional Formatting's rule rows and the Conditional Visibility editor's condition rows. Fixed at the shared CSS level (`.row-list-item`/new `.row-field-grid`): every direct child now gets an explicit `flex: 1 1 0`, sidestepping the corrupted-basis path entirely; buttons are excluded so they keep their natural small size. Verified across all four affected editors.
- **Device View's popover Save now matches the real app (fixed 2026-08-29)**: a masked `core.input` (FDWS v1.11) only commits its typed value on `blur`/`change`, and a popover's Save button reads that value at tap-time — if the field hadn't already lost focus (a real risk on touch, not something to depend on browser focus-shift ordering for), Save committed a stale/empty value instead of what was typed. `MockWidgetHost.js` now implements the same `flushPendingEdits()` fix as the real app's `CompositeWidget.js` (both driven by the shared `InteractionDispatcher.js`), so Device View's popover simulator behaves identically to production instead of happening to dodge the bug. Also: `core.input` now sets `enterKeyHint: 'done'`, so an on-screen keyboard dismisses the field instead of inferring a "Next" action toward a nearby one.
- **Local-state array persistence, including a session-only mode (FDWS v1.21/v1.22, added 2026-08-29)**: the State tab's Persist control is now a three-option select instead of a checkbox — "Don't persist" / "Persist (device storage)" / "Session only (this app run)" — since `type: "array"` state can now persist too (previously blocked unconditionally; only a live-synced array, one with a Sync From, still can't). "Session only" survives a widget being destroyed and rebuilt within the running app (e.g. switching pages) but resets on the next actual relaunch — for state that's meant to differ use-to-use rather than either resetting immediately or persisting forever. `StudioValidator.js` validates the new value and still warns on the array+Sync-From exclusion. Motivated by a real widget (COM1/COM2 collapsible radio) whose radio presets needed exactly this: distinct per flight, not stale from the last one.
- **Real curved arc gauges (FDWS v1.20, added 2026-08-29)**: `core.gauge`'s Transform dropdown gains "Arc" — a genuinely curved SVG sweep (radius, start/end angle, track/fill colors, line cap) instead of `arc-fill`'s straight-bar `scaleX()` hack — plus a Zone Bands editor for static caution/redline color segments (positioned by ratio of the value range, so they stay put if the sweep changes). First step of a broader push (see `../CHANGELOG.md`) to make every advanced instrument type — arcs, scrolling tapes, digit drums, tinted SVG faces — fully authorable here with no hand-edited JSON, after an audit found the existing Attitude Indicator (built on `props.compose`) had never actually been authorable in Studio when it was made.
- **Blank widget/popover templates declare the current FDWS version (fixed 2026-08-29)**: "New Widget" and "New Popover" previously stamped a hardcoded `fdws` (`"1.1"`/`"1.3"`) regardless of which fields you actually used building on top of them — a widget built entirely from v1.20 fields could still export declaring `"1.1"` forever. Both templates now stamp whichever version `FDWS_VERSIONS`' own latest entry is, so a freshly created widget always starts truthfully declaring what that build of Studio actually supports.
- **Tintable SVG faces, scrolling tapes, odometers, HSI pivot helper (FDWS v1.20, same day)**: the rest of that initiative — `core.image`'s new "Inline SVG" Render Mode (tintable via the existing Text Color field, including its Conditional Formatting rules), a new `core.tape` component (Avionics Controls palette) for scrolling airspeed/altitude/heading tapes, a "ODOMETER" option on `core.display`'s Value Format for a mechanical rolling-digit-drum readout, and a "Stack & Match Pivot" button in the canvas's multi-select toolbar for aligning several co-centered rotating `core.gauge` layers (an HSI's compass card + heading bug + course needle) in one click instead of hand-tuning col/row/w/h/pivot per layer.
- **Bundled popover export (FDWS v1.19, added 2026-08-28)**: exporting a widget (`.fdwidget`/JSON/clipboard) now inlines every referenced-and-saved `popoverWidgetId` into the export's `popovers` array, so a widget and the popover(s) it opens ship as one file instead of separate downloads — the recipient's import unpacks and installs them exactly as if each had been imported on its own. The export dropdown only prompts when a referenced popover isn't in your saved library yet (nothing to bundle for it); importing a bundle registers its popover(s) into your local library before loading the host widget. A same-day follow-up fixed two real bugs found live-testing this: Device View's popover modal chrome was hardcoded dark regardless of theme (now theme-aware via CSS custom properties), and the Design canvas's mock renderer could show a `core.label`/`core.button`/annunciator's Studio-authoring name instead of an intentionally-empty label (same class of bug as the real runtime's `LabelComponent.js`, fixed the same way — see `CHANGELOG.md`).
- **Manual per-theme styling (FDWS v1.18, added 2026-08-28)**: the widget root's "THEME" Inspector group sets which theme the widget is designed for (`baseTheme`) and whether the other theme keeps auto-deriving or is hand-authored (`themeMode`). Switching to Manual seeds every component's non-base-theme colors from what would currently auto-derive; from there, the Live Theme Preview toggle above doubles as "which theme am I editing" — while previewing the non-base theme, every component's (and the widget root's) Text/Border/Background Color fields target that theme's override instead of the base style, flagged with a small banner in the Appearance panel. Structural properties (border width/radius/style, background type, layout) always stay shared between both themes.
- **Hide layer groups/components in the editor** (added 2026-08-27): an eye toggle next to every component and layer group in the Layers tab dims it and skips it on the Design canvas — a scratch visibility aid for working on a busy widget, with zero effect on Device View or export (both always render everything; the hidden set lives only in `StudioState`, never in the widget definition).
- **Live local-state values** (added 2026-08-27): the State tab shows each declared `state[]` var's live current value alongside its default, updating in real time as you tap/type in Device View — confirms an interaction actually changed the state you expect instead of just trusting the binding is wired correctly.
- **Component outlines adapt to the widget's own background** (added 2026-08-27): the "Toggle Component Outlines" button's outline is computed per-render from the widget's own effective background lightness — light on a dark-authored widget, dark slate on a light one — instead of a single flat gray that all but disappeared against a dark widget (the common case).
- **Interaction triggers can be edited, not just added/removed** (added 2026-08-27): each card in the Behavior group's interaction list has a ✎ Edit button alongside ✕ Delete — opens the same Trigger/Action/Feedback form as "+ Add Interaction Trigger," prefilled from that trigger's own saved values, and updates it in place on submit instead of requiring delete-and-re-add.
- **Modals never close on an outside click** (fixed 2026-08-27): every Studio modal (confirm dialogs, Add/Edit Interaction Trigger, etc.) shares one dialog helper (`StudioModal.js`) that used to dismiss on any click landing on the backdrop — easy to trigger by accident on a wide form and previously discarded the in-progress form with no warning. Close via ✕/Cancel or Escape only now.
- **Divider Line (v1.17)**: `core.divider` — a plain grid-snapped horizontal or vertical separator, in the palette's Text & Display category. Sized/positioned on the grid like any other component; thickness, color, and dash style (solid/dashed/dotted) are set via the same Border controls every component's Property Inspector already has (`style.border.width`/`.color`/`.style` — the last one is new in v1.17 and works on any component's border, not just dividers), not a bespoke line-drawing tool.
- **Component Palette**: Searchable and grouped by category (Text & Display, Buttons & Inputs, Avionics Controls, Data & Composition) — Label, Button, Rotary, Display, Annunciator, Stepper, Image, Container, plus the v1.2 additions — Gauge, Slider, Selector, Rocker, List, Reference, and Touch Pad.
- **Widget Popovers (v1.3)**: Author a widget with `kind: "popover"` ("New Popover" in the bottom bar) instead of the default `kind: "widget"` — it's excluded from the page-layout picker and only ever opened as a modal. `StudioInspector.js`'s "Add Interaction Trigger" modal builds `core.openWidgetPopover`'s `context` map (symbolic key → `stateRef`/`writable`/`applyOn`) as an editable list of rows, and choosing a `popoverWidgetId` uses a real `<select>` populated from your saved `kind: "popover"` widgets — not a free-text id, per the spec's authoring-tool guidance. Device View renders an open popover live via `widgets/components/WidgetPopoverModal.js` + `widgets/components/MockWidgetHost.js` (a Studio-only stand-in for the PWA's real `CompositeWidget`, since Studio has no widget-hosting runtime of its own), so `$context`/`core.commitToHost` round-trips can be tested before export.
- **Specification Validator**: Real-time §11 compliance checks (bounds, grid alignment, color contrast, SimVar bindings), including v1.3's `kind`/`popoverWidgetId`/`contextKey` rules (`StudioValidator.js`). Validation is now *live*, not just on-demand: an always-visible error/warning count badge sits next to the "Validate (§11)" button, invalid/warned components get a badge directly on the canvas and in the layer tree, and every message in the full validation-report modal is clickable — clicking one selects the offending component so you don't have to hunt for it.
- **Conditional Visibility & Guard**: the Inspector's "VISIBILITY & GUARD" panel authors `visibleWhen` (allOf/anyOf condition lists against a declared state var, or — via each condition's "Custom / nested path…" option, FDWS v1.13 — a nested/indexed path like `presets[0].label`, with a JSON escape hatch for hand-authored nested-compound expressions) and the guard safety-cover overlay (`layout.guard`) — both were runtime-supported since FDWS v1.2 (nested paths since v1.13) but had no authoring UI before.
- **Live Sim Bench**: Built-in telemetry simulator for testing live widget bindings, driven by the canonical Deck Events list (grouped by category) instead of a hardcoded pre-Deck-Events-unification key list, plus three one-click scenario presets (Cold & Dark / Cruise / Approach).
- **Canvas multi-select & align**: shift-click to multi-select components; a floating toolbar appears with align-left/right/top/bottom/center and distribute-horizontal/vertical, operating on exact grid units (`col`/`row`/`w`/`h`), all as one undo step.
- **Layer group drag-to-reorder**: drag a layer group's header to reorder it in the Layers tab — reassigns every group's Z-offset automatically instead of hand-tuning numeric Z fields.
- **Community Deck Events Packs**: import a shareable JSON pack of extra logical binding-name suggestions (e.g. for a specific G1000/G3000 aircraft) from the Library tab, or export the custom names your own saved widgets already use so you can hand the file to someone else. See "Community Deck Events Packs" below.
- **Library tab's built-in templates are collapsed by default** (added 2026-08-27): the FDWS templates gallery used to open expanded, so reaching your own saved widgets/popovers below meant scrolling past all of it every time. Now a collapsed `<details>` section — click to expand, your saved library is right at the top either way.
- **Import & Export**: Package widgets as `.fdwidget` or `.json` for use in [Flight Deck PWA](../flight-deck-pwa) — as of FDWS v1.19, a widget's referenced popover(s) bundle into the same file automatically (see above).

## Run locally
```bash
npx serve .
```
or just open `index.html` directly in a browser.

## Widget components
`widgets/components/`, `widgets/definitions/`, `core/SecurityValidator.js`, `core/deckEvents.js`, `core/widgetVarExtractor.js`, and `core/deckEventPacks.js` are synced from [`../shared/`](../shared) — this app must render widgets identically to Flight Deck, so don't hand-edit these; see the root [README](../README.md).

## Deck Event binding picker
`StudioInspector.js`'s "SIMVARS & BINDINGS" panel picks read/write bindings from `shared/deckEvents.js`'s canonical default list (a `<select>`), with a "Custom…" option that reveals a second dropdown merging two sources — Deck Events already used by another widget in this Studio's saved-widget library (`state.loadSavedWidgets()`, via `shared/widgetVarExtractor.js`'s `extractCustomDeckEvents()`), and any names suggested by an imported Community Deck Events Pack (see below) — plus a free-text field for a brand-new custom name or a raw SimVar/H:/L:/K: escape-hatch value. See [`../CHANGELOG.md`](../CHANGELOG.md) for the full writeup — this replaced a hardcoded, PC-Bridge-unaware `COMMON_SIMVARS`/`COMMON_EVENTS` suggestion list.

## Community Deck Events Packs
Added 2026-08-23 (`../shared/deckEventPacks.js`, synced into `core/deckEventPacks.js`). A "pack" is a small JSON file of extra `{name, kind, category, label}` logical-name suggestions — same shape as `deckEvents.js`'s canonical `DECK_EVENTS`. It's purely an authoring-time convenience for the binding picker above: importing a pack never changes what a widget does at runtime, since every bare logical name is already host-defined per FDWS v1.4 §1.2, and PC Bridge's `profileManager.js` already auto-registers any name a widget actually uses as an unmapped placeholder the moment it's installed (Appendix B item 3) — whether or not a pack ever suggested that name. That's also why this feature needed **no PC Bridge changes**.

In the Library tab (`StudioLayersPanel.js`, bottom "COMMUNITY DECK EVENTS PACKS" section):
- **Import Pack…** reads a `.json` pack file and validates it (`parsePackFile()` — rejects a pack event name that collides with a canonical Deck Event name), then stores it in this browser's `localStorage` (`fdws_deck_event_packs`).
- **Export My Custom Names…** scans your saved-widget library for custom (non-canonical) logical names already in use (the same scan the binding picker's "used by" suggestions come from) and downloads them as a shareable pack JSON, with a name/author/description you fill in.
- Imported packs are listed with an event count and a Remove button.

Flight Deck PWA has the equivalent Import/Export UI in its Settings page — see [`../flight-deck-pwa/README.md`](../flight-deck-pwa/README.md). The two apps' imported-pack lists are independent (each app's own `localStorage`); the pack JSON file is the sharing unit between them, and between different users.
